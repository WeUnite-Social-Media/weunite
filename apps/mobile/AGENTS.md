# Mobile Agent Notes

## Scope

This package owns the Flutter mobile client in `apps/mobile`.

## Responsibilities

- Render the mobile application for auth, feed, opportunities, chat, and profile flows.
- Consume the Spring API through explicit REST clients under `lib/core/network`.
- Keep feature code organized with Clean Architecture boundaries: `data`, `domain`, and `presentation`.
- Mirror mobile-facing design patterns from `apps/web`, especially header/bottom navigation, cards, badges, forms, and color tokens.

## Does not own

- Backend business rules.
- Web-specific rendering logic.
- Shared JavaScript or TypeScript tooling packages.

## Key entrypoints

- `lib/main.dart`: only calls `runApp(WeUniteMobileApp(dependencies: bootstrap()))`.
- `lib/app/bootstrap.dart`: builds `AppConfig`, `TokenStorage`, `SessionEvents`, `ApiClient`, and every repository into an `AppDependencies` bundle.
- `lib/app/app.dart`: root `WeUniteMobileApp` widget — `MultiRepositoryProvider` + the session-wide `AuthCubit` at the top, `AuthCubit` state drives which branch renders.
- `lib/core`: configuration, Dio client, token storage, theme, widgets, and error handling.
- `lib/features/*`: feature-owned data, domain, and presentation code.
- `pubspec.yaml`: Flutter dependencies and assets.

## Working rules

- Keep the app frontend-only; backend domain behavior must stay in `apps/api`.
- Read API contracts from `apps/api` and mirror existing web client requests before adding mobile endpoints.
- Configure API hosts with `--dart-define=WEUNITE_API_URL=...`; do not assume Vite proxy behavior.
- Keep secure session state in `flutter_secure_storage`, not plain preferences.
- Collection reads for posts, comments, opportunities, conversations, and messages return top-level JSON arrays; login (`AuthDTO`), user/profile reads, and follow counts use `ResponseDTO.data`.
- Debug HTTP diagnostics live in `core/network/api_diagnostics.dart`. Log metadata and error types only, never credentials, headers, query values, or message bodies.
- There is no `/auth/refresh` endpoint on the API today (only `jwt` + `expiresIn` are issued on login). `ApiClient` does not retry on 401: an authenticated request that gets 401 clears the stored token and notifies `core/session/session_events.dart` (`SessionEvents.onExpired`), except for `/auth/login`, whose 401 means a bad credential, not an expired session. `AuthCubit` listens to `onExpired` and moves to `unauthenticated` with a session-expired message. `TokenStorage` also persists the access token's expiry instant so `AuthRepositoryImpl.restoreSession` treats an expired or orphaned (token without cached user) token as no session.
- **Session-scoped cubits**: only `AuthCubit` lives above `MaterialApp`. `FeedCubit`, `OpportunitiesCubit`, `ChatCubit`, and `ProfileCubit` are created inside the `authenticated` branch of `lib/app/app.dart`, wrapped in a `MultiBlocProvider` keyed with `ValueKey(user.id)`. That key forces the whole subtree (cubits + `AppShell`) to be torn down and rebuilt whenever the logged-in user changes, so a new session never sees stale state from the previous user.
- **Tab navigation**: `AppShell` renders the four tabs with `IndexedStack` (not a rebuilt `switch`), so each tab screen is created once per session and keeps its scroll position and cubit state when the user switches tabs. Each screen's `initState` only triggers its initial load when `state.hasLoaded` is still `false`; pull-to-refresh always forces a reload by calling the cubit method directly.
- **Load vs action errors**: feature states expose `loadErrorMessage` (consumed by `AsyncStateView`, only set when there is no data to show) and `actionErrorMessage` (shown as a `SnackBar` via a `BlocListener`/`BlocConsumer` and cleared right after, via each cubit's `dismissActionError()`). A failed reload that happens while data is already present (e.g. pull-to-refresh, pagination, like/comment/post actions) always reports through `actionErrorMessage` so the existing list stays on screen instead of being replaced by the full-screen error view.
- **State `copyWith`**: error fields use a `ValueGetter<String?>?` parameter (`import 'package:flutter/foundation.dart'`) instead of a plain nullable value, so omitting the parameter really means "keep the previous value" and passing `() => null` really clears it. Follow this pattern for any new nullable state field that must be explicitly clearable.
- Bottom sheets opened from a screen whose cubit now lives inside the `authenticated` branch (e.g. `CommentsSheet`, `CreatePostSheet` from `FeedScreen`) must re-provide that cubit explicitly with `BlocProvider.value(value: context.read<FeedCubit>(), child: ...)` in the `showModalBottomSheet` builder — modal routes are siblings of the route that hosts the provider in the widget tree, not descendants, so ambient `context.read` lookups fail otherwise.
- **Current user id**: don't read `context.read<AuthCubit>().state.user?.id` in screens/widgets to act on behalf of the signed-in user or pass it into a cubit/repository call. `core/session/current_user_provider.dart` defines `CurrentUserProvider` (`currentUserId`, `requireUserId()`, which throws `AppException('Sessão inválida.')` when there is no session), implemented by `AuthCurrentUserProvider` on top of `AuthRepository.currentUser`. `bootstrap()` builds one instance and injects it into `FeedRepositoryImpl`, `ChatRepositoryImpl`, and `ProfileRepositoryImpl`, which resolve the id internally instead of taking a `userId` parameter (`FeedRepository.toggleLike/createPost/createComment`, `ChatRepository.getConversations/getMessages/sendMessage`, `ProfileRepository.getMyProfile`/`toggleFollow`). `ProfileRepository.getProfile(int userId)` is the one exception that keeps an explicit id, because it looks up someone else's profile rather than the caller's own. The message bubble widget in `ConversationScreen` is the one allowed exception to read `state.user?.id` directly, purely to decide left/right alignment for display — it never forwards that id anywhere. Follow this pattern for any new repository method whose id is always the logged-in user.
- **Chat realtime**: `ChatRealtimeClient` (`features/chat/data/chat_realtime_client.dart`) opens a single STOMP-over-SockJS connection per session, lazily on the first `watchConversation` call. The API only publishes on `/topic/conversation/{id}` — new messages, edits (full `MessageDTO` with `edited: true`), and deletions (a `{"type":"DELETE","messageId":...}` map, not a `MessageDTO`) all arrive on that same topic; `parseChatRealtimeEvent` in `chat_models.dart` discriminates between them. Sending goes through `/app/chat.sendMessage` with a `jsonEncode`d body (never hand-built JSON strings, which break on quotes/backslashes/newlines). The `stomp_dart_client` package freezes `stompConnectHeaders` and has a fixed `reconnectDelay`, so reconnection is handled by us: `reconnectDelay: Duration.zero` plus our own exponential backoff (1s–30s) that rebuilds the `StompClient` from scratch each attempt and rereads the token from `TokenStorage`. On reconnect, subscribers receive a `ChatRealtimeReconnected` event so `ConversationCubit` can resync via REST (`GET /conversations/{id}/messages/{userId}`) in case messages were missed while disconnected. `ChatRepository.getMessages`/`sendMessage` take no `userId`/`senderId` parameter — `ChatRepositoryImpl` resolves it from `CurrentUserProvider`. `ChatRepository.disconnectRealtime()` is called from a `BlocListener<AuthCubit, AuthState>` in `lib/app/app.dart` whenever the session leaves `authenticated` (logout or session expiration); that same listener does `popUntil((route) => route.isFirst)` on the app's `navigatorKey`, because `ConversationScreen` is a pushed route that survives switching the `MaterialApp.home` otherwise. There is no read-receipt broadcast (`/topic/conversation/{id}/read` only fires from `/app/chat.markAsRead`, which nothing calls today) and no mobile UI yet for marking a conversation as read. `ConversationDTO` only exposes `participantIds`, with no notion of "the other participant" (unlike the entity/attribute-shaped `recipient`/`user` this used to be parsed as); `ChatRepositoryImpl.getConversations`/`getConversation` resolve the peer the same way `apps/web`'s `ChatLayout.tsx` does — the first id in `participantIds` that isn't the current user — then fetch `GET /user/id/{id}` for its name/username/avatar, once per unique peer id per call (`Future.wait`, deduplicated), treating a 404 as "no profile" (`peerName` stays `null`) rather than failing the whole list.
- **Routing (`go_router`)**: `lib/app/router.dart` builds the single `GoRouter` used by `MaterialApp.router` in `lib/app/app.dart`. Route map: `/splash` (shown while `AuthCubit.state.status == checking`), `/login`, `/signup`, a `StatefulShellRoute.indexedStack` with branches `/feed`, `/opportunities`, `/chat`, `/profile` (replaces the Fase 2 manual `IndexedStack`; `AppShell` now takes a `StatefulNavigationShell` and calls `navigationShell.goBranch(index, initialLocation: ...)` from `AppBottomNav`, which still preserves each tab's scroll position and cubit state), and three top-level pushed routes: `/chat/:conversationId` (resolves the id to a `Conversation` via `ChatRepository.getConversation`, added for this route, before rendering the existing `ConversationScreen`), `/profile/:userId` (a new route-scoped `UserProfileCubit` + `UserProfileScreen` showing a third party's profile; distinct from the session-scoped `ProfileCubit`, which only ever holds the signed-in user's own profile), and `/posts/:postId` (`PostDetailScreen` is a placeholder — `GET /posts/get/{postId}` exists on `PostController` but returns `ResponseDTO<PostDTO>`, with `likes`/`comments` lists instead of the counters `FeedPostSummaryDto` parses; wiring it is still pending). A top-level `redirect` reads `AuthCubit.state.status` and a `GoRouterRefreshStream` (wraps `AuthCubit.stream` as a `Listenable`) re-runs it on every auth change: unauthenticated → `/login`, authenticated while on `/login`, `/signup`, or `/splash` → `/feed`, `checking` → `/splash`. The session-scoped `MultiBlocProvider` (`FeedCubit`, `OpportunitiesCubit`, `ChatCubit`, `ProfileCubit`, keyed by `ValueKey(user.id)`) now lives inside the `StatefulShellRoute`'s `builder`, so it is only ever built while authenticated and is torn down/rebuilt exactly as it was above `AppShell` before the `go_router` migration. `AuthCubit` itself and the `GoRouter` instance are created once in `_WeUniteMobileAppState.initState` (not lazily in `build`) because the router's `redirect`/`refreshListenable` need a concrete `AuthCubit` up front; both are closed/disposed in `dispose()`.
- **Typed API contracts**: DTOs live in `features/*/data` (e.g. `feed/data/feed_models.dart`) or, when shared across features, in `lib/core/contracts` (`UserDto`, `UserSummaryDto`, `SkillDto`, `ResponseDto`). Every DTO field uses the API's exact name — no `@JsonKey(name:)`, no reading alternate keys (`content ?? description ?? text`), no defaulting an invalid or missing value (`?? ''`, `?? 0`, `DateTime.now()`, `tryParse`). A field the DTO doesn't declare (e.g. `id` as a JSON string vs. a JSON number, handled by `core/contracts/json_converters.dart`'s `StringIdConverter`) or a value of the wrong shape (invalid enum, invalid date, missing required field) throws (`TypeError`, `FormatException`, or `ArgumentError`), which `mapDioError` in `core/network/api_client.dart` turns into `AppException('Resposta do servidor em formato inesperado.')` — never a silently wrong value. `*.g.dart` files are committed (not generated in CI), because `turbo`/`flutter test` run without codegen; run `pnpm --filter @weunite/mobile codegen` (`dart run build_runner build --delete-conflicting-outputs`) after touching any `@JsonSerializable` class. `pnpm --filter @weunite/mobile contracts:update` refreshes `openapi/weunite-api.json` from a running API (`--origin` or `WEUNITE_API_ORIGIN`, default `http://localhost:8080`); it requires the API to be up and is not run in CI. `test/contracts/openapi_contract_test.dart` checks that the fixtures in `test/fixtures/api_payloads.dart` (and the request DTOs' `toJson()`) match the schemas and paths in that spec file, so a spec update surfaces any drift as a test failure. Known gap: the STOMP chat payloads (`MessageDeleteEventDto`, `SendMessageRequestDto`) aren't in the OpenAPI spec at all (it only documents REST), so they're typed by hand from `ChatController.java` and the contract test doesn't cover them.
- **Post events (feed ↔ profile sync)**: `features/feed/domain/post_events.dart` defines `PostEvents`, a session-scoped broadcast bus provided by a `RepositoryProvider<PostEvents>` that wraps the session `MultiBlocProvider` in `lib/app/router.dart` (the `ValueKey(user.id)` now sits on that `RepositoryProvider`, so the bus is rebuilt with the cubits). Events: `PostCreated` (every post list reloads), `PostUpdated(post)` (lists holding that id replace it — published by `FeedCubit`/`ProfilePostsCubit` after an optimistic like and again on revert), and `PostCommentAdded(postId)` (lists bump the counter — published by `CommentsSheet`, not by a cubit, so the comment counts exactly once per list). A cubit that publishes also receives its own `PostUpdated`; replacing a post with an equal one is a no-op. Don't call another screen's cubit to keep lists in sync — publish on `PostEvents` instead. Open the create-post and comments sheets through `showCreatePostSheet(context)` / `showCommentsSheet(context, postId:)`, which re-provide `FeedRepository`/`PostEvents` to the modal route.
- **Profile posts**: the "Posts" tab of `ProfileScreen` lists the signed-in user's posts through the session-scoped `ProfilePostsCubit` (`FeedRepository.getMyPosts`, `GET /posts/get/user/{userId}`, paginated with `kFeedPageSize`), with like/comment, pull-to-refresh (profile + posts) and infinite scroll. Tabs render their section inline in the page `ListView` (no fixed-height `TabBarView`), so the list grows naturally. Third-party profiles (`UserProfileScreen`) don't list posts yet.
- **Post images**: `CreatePostSheet` picks one image from the gallery with `image_picker` (Android photo picker, no extra manifest permissions; downscaled to 2048px / quality 85, rejected above 10 MB to match `spring.servlet.multipart.max-file-size`). `FeedRemoteDataSource.createPost` sends it as the optional multipart `image` part next to the JSON `post` part, typed by extension (`imageMediaTypeFor`), and the API uploads it to Cloudinary — so `CLOUDINARY_URL` must hold real credentials for uploads to work locally. A post may be image-only (empty `text`). `PostCard` caps rendered images at 420px and shows a placeholder while loading or on failure.
